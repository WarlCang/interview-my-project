# PRODUCT.md — what this is and refuses to be

## Users

Vibe coders with portfolio projects facing technical interviews: students, career
switchers, bootcamp grads. The emotional driver is specific — the fear of being asked
*"walk me through why you built it this way"* about code an agent wrote.

## Purpose

One sentence: **Vibe coding got you the project. interview-my-project makes it yours.**

The tool succeeds when a user walks into a real interview and every question about
their project feels like a rerun.

## Personality

The interviewer is a skeptical senior bar-raiser: assumes an agent built your project
and you watched, doubts the project matters, and makes you talk it out of both. Every
jab is earned by evidence from your code or session logs — never generic negging,
never personal. Land a real answer and the skepticism drops for a beat. The coaching
that follows each answer is 100% constructive.

## Design principles

1. **The question bar is the product.** Every question must pass one test: you can't
   answer it by reading a single file for 10 seconds. If the questions feel like a
   quiz generator, the product is dead.
2. **Realistic interviewer, omniscient answer key.** Questions sound like someone who
   skimmed your README; scoring cites `file:line` and your own session logs. The
   asymmetry is the design.
3. **Grounded or silent.** Every verdict, jab, and coaching line traces to actual code
   or logs. No evidence, no claim.
4. **Honest scores only.** A candidate who walks into a real interview overconfident
   because we were polite is the product's failure mode.
5. **Local everything.** Repo, session logs, scorecard — nothing leaves the machine.
   Runs on the user's own agent subscription. Zero infrastructure, forever.
6. **Any language, same bar.** The persona is re-created natively per language, never
   translated; the taxonomy, ranking, and rubric are language-invariant.
7. **The room decides the questions.** Not every project is technical, and not every
   interview is an engineering interview. Probes come from what the project actually
   contains and the role the candidate is targeting — the same repo gets a different
   interview for a PM, design, data, or engineering room, run by the skeptical
   senior of that discipline. Never a fixed template.

## Anti-references (what we refuse to become)

- Real-time interview assistance — that's cheating tooling. Never, in any form.
- Generic interview prep — "explain Big-O" content is a crowded graveyard. The repo
  is the subject, always.
- A quiz generator — numbered trivia with a score at the end.
- A flatterer — tools that make you *feel* prepared sell better and fail their users.
